# テロップ切り分けルール ([CHANNEL]ch)

## 背景

2026-04-11 の No.801「音声生成AI徹底比較」SRT 生成セッションでの学び:

1. **最初**: whisper CLI で単純転写 → 粒度不明、品質低
2. **v2 アプローチ (失敗)**: fugashi + 品詞ベース Tier ルール → 冒頭8件は 8/8 一致したが、動画全体を見ると「思って/いるので」「検証して/いきたい」のような複合動詞分断が多発。rule-based は日本語の「て形+補助動詞」の全パターン（20以上）をカバーできず、破綻
3. **v3 アプローチ (現在)**: LLM が全文を読んで違和感を検出・修正する QA ループ方式。スキル (`~/.claude/commands/srt.md`) に必須ステップとして組み込み済み

ユーザーの原指摘 (2026-04-11):
> 「文字数を意識しすぎて、テロップの切り替えタイミングが支離滅裂になっている」
> 「文字起こし→テロップの切り替わるタイミングで1行ずつ並べる→違和感を探す→直す→最終チェックをする」

**v3 ワークフローは上記のユーザー提案を忠実に実装したもの**。

## /srt の責務範囲（2026-04-19 確定・最重要）

次回以降のすべての分析・改善の前提となる原則:

### 1. /srt は「喋りの意味単位」で区切る。編集者の物理的再分割は模倣しない

完成版 XML のテロップは、/srt の出力を**編集者が1行の物理制約に収めるために更に分割**した結果であって、新たな言語ルールを示すものではない。

- ✗ NG: 「固有名詞の前で切る」「て形＋補助動詞の境界で切る」「前置詞節の後で切る」を **/srt のルール化しない**
  - これらは編集者が「1行に収まらないから仕方なく切った」位置で、/srt 側の切り分けは既に正しい
- ✗ NG: 「18字以上は必ず分割」のような**文字数ハード制約も入れない**（文字数カウントに気を取られて変な所で切る副作用が出る）
- ✓ OK: 既存の「意味の区切りで切る」「複合動詞句は分断しない」ルールを維持

### 2. /srt は喋っているすべての行を出力する。不採用判定をしない

完成版で挨拶や列挙が別グラフィックに差し替わっていても、/srt 側では**喋った全行を SRT に残す**。理由:

- SRT の行を省くとタイムコードがズレて、後工程の Premiere インポートで字幕位置が狂う
- 「この行は採用されない」の判断は編集者の領域
- 例: `皆さんこんにちは` が最終動画で名前テロップに差し替わっていても、SRT には残す

### 3. 句読点（、。）は使わない

/srt 出力では読点「、」句点「。」を使わない。固有名詞・中黒・半角スペースは許容。

### 4. 英数字前後の半角スペースは自動挿入しない

「ひらがなが連続して読みにくい」等の可読性調整は**人間判断**。AI が機械的に挿入すると崩壊する。既存の「話者ポーズ (word gap ≥ 300ms)」と「英語プロダクト名内部の正規表記」による半角スペースのみ維持。

### 5. フィラー「ちまちま」等の完全削除はしない

完成版で削除されているように見えても、強調テロップ (V5) に移されているケースが多い。/srt (V4 相当) 側では**発話通り残す**。既存の「こう」「ちょっと」保護ルールと同じ方針。

### 6. Whisper 誤認識の辞書化は「再出現する固有名詞」のみ

一回限りの文脈誤認識（例: `ライブ→例文`、`糸を組む→意図を汲む`）は辞書に入れない。コンテキストがパンクして全体の品質がむしろ劣化する。辞書追加の基準は「**チャンネル内で再登場する固有名詞か**」のみ。

### 学習元

2026-04-19 No.809 ClaudeCode × Renoise × Remotion セッション。完成版 XML (587 ユニークテロップ) と /srt 出力 (541 行) の差分分析で、編集者側の分割 39 件 / 書き換え 41 件 / 不採用 32 件を検出。**大半は /srt ではなく編集者の物理制約・グラフィック差替えに起因するもの**と判明し、/srt 側での学習対象から除外。

## 絶対禁止パターン (ハード制約)

以下に該当する切り方をした時点でNG。必ず修正する。

### 1. 文頭フラグメント禁止

以下で始まるテロップは作らない。発生したら前のテロップと統合する:

- **助詞単独**: 「か」「も」「を」「に」「が」「は」「の」「と」「や」「ね」「よ」「ぞ」
- **「で」** (接続詞「でも」「です」「では」以外の単独「で」)
- **動詞活用語尾**: 「ます」「まし」「ません」「でした」「きます」「きる」「きれ」「きない」「きて」
- **否定/派生**: 「ない」「なく」「ではなく」「じゃなく」「じゃない」「ではない」「なっ」
- **複合動詞の後半**: 「きており」「きました」「きます」（「〜ている」「〜てきた」「〜ていく」の後半）
- **連体接続**: 「という」「として」「について」「によって」「にとって」
- **抽象名詞単独**: 「ため」「とき」「はず」「こと」「もの」 + 助詞
- **カタカナ破片**: 「ベル」「ース」「トル」「ション」「ング」「タイ」「ティ」「ント」等

### 2. 複合動詞句の分断絶対禁止（No.801 で発生した致命的エラー）

以下は 1 つの動詞句として扱い、分断しない:

- **「〜ている」** → 「思って/いる」「見て/いる」「なって/いる」等は全部 1 単位
- **「〜ていく」** → 「検証して/いく」「変わって/いく」等は 1 単位
- **「〜てくる」** → 「なってくる」「出てくる」等は 1 単位
- **「〜てみる」** → 「試してみる」等は 1 単位
- **「〜ておく」** → 「やっておく」等は 1 単位
- **「〜てしまう」** → 「忘れてしまう」等は 1 単位
- **「〜てほしい」** → 「見てほしい」等は 1 単位
- **「〜てくれる」** → 「教えてくれる」等は 1 単位
- **「〜てあげる」「〜てもらう」「〜てやる」** → 全部 1 単位
- **「〜てもいい」「〜てはいけない」「〜てこそ」** → 全部 1 単位
- **派生形**: 「〜ている所」「〜ていこう」「〜ていかない」「〜ていくので」「〜ており」「〜ています」等全部 1 単位

### 3. 動詞活用の中断禁止

- 「でき/ます」「き/ました」「し/ている」「され/ない」等で切らない
- 動詞語幹と活用語尾の境界は**必ず語幹の終わりまで1単位**

### 4. 「た + 連体修飾名詞」の分断禁止

「〜た + こと/もの/とき/はず/ため」のパターンは連体修飾句として 1 単位扱い:

- ✗ 「AIの音声だった / ことに気づきました」
- ✓ 「AIの音声だったことに気づきました」

### 5. 「ということで/は/です」の分断禁止

「と + いう + こと + で/は/です」は複合終止表現として一体扱い。

### 6. カタカナ語の分断禁止

「レ/ベル」「ミニ/マックス」「エ/モーション」等で切らない。

### 7. 固有名詞の分断禁止

「[CHANNEL]」「MiniMax Audio」「Fish Audio」「ElevenLabs」「LINE登録」「VOICEVOX」等は一体扱い。

### 8. 「か」で終わる質問を含めて終わらせる

「気づきましたか」で1テロップ。「か」だけを切り離さない。

## 優先ルール（ソフト）

1. **文末 + 新トピック開始で切る** — 「[NAME]です」の後は「今回は」から新テロップ
2. **「〜ではなく + 新主語」で切る** — 「声ではなく」の後は「AIの音声〜」
3. **複合表現は一体扱い** — 「なくなったんじゃないかということで」を 1 テロップ
4. **短いテロップ許容** — 4-8字でも意味の区切りならOK（例: 「人間が話す必要が」8字）
5. **話者ポーズを半角スペース** — word gap ≥ 250ms で半角スペース（助詞前後には入れない）

## 失敗例と学び (No.801 v2 でやらかしたケース)

### 致命的エラー: 「思って / いるので」
- **何が起きたか**: 「思っているので」という進行形を「思って」と「いる」で分断
- **原因**: fugashi が「て」(接続助詞) と「いる」(動詞) を別形態素として分類し、品詞ベースルール Tier B が「接続助詞 + 動詞 = 切断可能」と判断した
- **視聴者から見た問題**: 「いるので」(4字) が単独テロップになり、意味不明になる
- **対策**: 「〜て + いる/いく/くる/みる/おく/しまう」を絶対不可分として扱う

### 同類エラー: 「検証して / いきたいと思います」
- **原因**: 「検証していく」を「して」と「いく」で分断
- **対策**: 同上

### 文頭フラグメント: 「か2026年」
- **何が起きたか**: 「気づきましたか」の「か」が次テロップの頭に移動
- **原因**: 品詞ベース emit で「気づきまし | た | か | 2026」と分解した時、「か」を次グループの頭に送ってしまった
- **対策**: 終助詞「か」は常に前のテロップの最後

## v5 ワークフロー（2026-04-18 採用・現行）

v4 の 3エージェント構成（Agent2/3）は**廃止**。メインセッション内で LLM が意味区切りの改行テキストを直接ファイル書き込みし、スクリプトで SRT 化する方式に切り替え。

```
[機械]   Whisper(large-v3, beam=1, VAD) → segments.json        [約7分]
[LLM]    fulltext.txt を Read → lines.txt を Write              [約3分]
[機械]   --from-text で lines.txt + segments.json → SRT        [約0秒]
─────────────────────────────────────────────────────────
合計: 約10〜15分（実測: 28分音声で13分34秒）
```

### 切り替え理由（2026-04-18 ClaudeCode × Renoise × Remotion セッション）

- v4 の Agent2 が **22分**、Agent3 はさらに数分 → 合計 30分超
- メインセッションでチャットに直接改行テキストを出した結果、**クオリティは同等以上**で **1〜2分**で完了
- ユーザー指示: 「スピード重視でやってほしい。このクオリティを出せればいい」
- Step C（ユーザー確認）も不要判断（自律動作でクオリティが出れば OK）

### v5 の改行ルール（重要）

- **意味の区切りで切る**（文字数より意味優先、5〜25字目安だが縛られない）
- **複合動詞句は分断しない**（「〜ている」「〜ていく」等）
- **副詞句は次行の先頭**（「徹底的に」「本当に」等）
- **話題転換で切る**（説明→CTA、概念→具体例、肯定→疑問）
- **「〜おり/ており」「〜ですけども」で切る**
- **フィラー「こう」「ちょっと」は文脈判断で残す**（全削除禁止）
- **固有名詞は必ず修正**（`telop_channel_patterns.md` のチャンネル表記ルールを参照）

### v5 の累積ズレバグと修正（2026-04-18 ClaudeCode × Renoise × Remotion セッション）

**症状**: 生成 SRT を Premiere にインポートすると、字幕が徐々にズレていく（動画終端で 20〜30秒 のズレ）。

**原因**: `assemble_from_text` の Whisper 単語処理で `apply_corrections` が単語単位で適用されていたが、Whisper の単語は細切れ（例: `A`,`IC`,`カ`,`ラ`,`ボ`）で、辞書置換「AICカラボ→[CHANNEL]」が発動しない。一方 lines.txt 側は行単位で置換されるため、Whisper 側と lines 側で文字数が毎回 +1〜+3 ずつズレ、累積マッチングが狂う。

**修正**（`scripts/whisper_to_srt.py:892-940`）:
- segment 単位で words を連結して `apply_corrections` を試す
- 置換が発生した segment は、corrected 文字列を seg.start〜seg.end で文字単位の線形配分に切り替え
- 置換なしの segment は従来通り単語レベルの精密な時刻を維持

**教訓**: lines.txt 側で固有名詞を正規化するなら、Whisper 側も同じ正規化を seg 単位で行わないと累積ズレが発生する。CORRECTIONS 辞書に載っていない手動修正でも、文字数差（例: `NH→[COMPANY]` は +2字）が累積ズレを生む。辞書に追加するか、lines.txt を Whisper 原文表記にするかのいずれか。

### v5 のアンカー逆戻り防止修正（2026-04-26 No.822 中国の動画生成AI）

**症状**: lines.txt に存在する行が SRT に出力されない（324行 → 320エントリ）。具体的には `皆さんはどの...` 等が欠落し、前後の行が同じタイムスタンプ（`00:00:10,043`）になっていた。

**根本原因**: `assemble_from_text` の `_local_anchor` が `lo = max(0, expected_pos - SEARCH_RADIUS)` で検索下限を算出していた。類似した行頭6字（例: `Soraが使え`）が近接して2回出現する場合、`str.find()` が最左位置（既に処理済みの前の行の位置）を返してしまい、誤った時刻が付与される。結果的に `refine_timing` が duration=0 のエントリを削除して行が消える。

**修正**（`scripts/whisper_to_srt.py`）:
- `min_pos = 0` を `_local_anchor` の定義前に追加
- `lo = max(min_pos, expected_pos - SEARCH_RADIUS)` に変更（前エントリ終端より前を検索しない）
- `pos += line_len` の後に `min_pos = pos` を追加

**教訓**:
- 類似フレーズの近接出現（特に「〜が使え」等の動詞活用）でこのバグが発生しやすい
- `refine_timing` が duration=0 エントリを削除するため、誤マッチは「行の消滅」として顕れる
- SEARCH_RADIUS/PROBE_LEN を変えても根本解決にならない。下限制限が本質的な修正

### v5 の累積文字数ベース時刻引きバグとアンカー再同期修正（2026-04-26 No.822）

**症状**: SRT が動画後半ほど Whisper 真値より遅れる。`もちろんこれが1本` で +0.47s、`こういうシンプル` で +0.92s、`全然違うくないですか` で +3.02s と progressive に拡大。

**原因**: `assemble_from_text` (`whisper_to_srt.py:1000-1042`) は lines.txt の累積文字数を Whisper の連結文字列の文字位置として 1:1 に対応させ、その位置に対応する単語の時刻を引く設計。だが lines.txt は LLM が固有名詞を正規化したり意味区切りで整える工程で **Whisper 原文と微妙に文字数が異なる**（例: `カラボ→化ラボ` で +1字、`AI周囲カラボ→[CHANNEL]` で +3字、フィラー削除で −数字）。これらが累積し、後半の lines.txt 文字位置が Whisper 文字位置と数十字ズレ → 引く時刻が後ろの単語のものになる。

**修正**: 各行で行頭 6 字を Whisper 連結文字列の `pos ± 60` 文字範囲で局所検索し、ヒットしたら累積ポインタをそこへ再同期する（短い相槌行はスキップ）。No.822 では 32 行で再同期発動、累積 drift -15 字を補正、最終 drift は全箇所 ±0.1s 以内に収束。

**教訓**:
- 「lines.txt の文字数を変えても Whisper word 時刻は変わらない」のは正しい。問題は **時刻を引くキーが文字位置だった** こと
- 文字位置ベースのマッピングは便利だが累積誤差に弱い → 一定間隔で **意味的アンカー** で再同期するのが堅牢
- 6:24 でぴったり、その後ズレが拡大、という非線形 drift は、累積文字数の +/- がたまたま中盤で相殺している兆候

### v5 のオフセット誤加算バグと修正（2026-04-26 No.822 中国の動画生成AI セッション）

**症状**: SRT 全エントリが本来より +2.8秒 後ろにズレ、Premiere タイムラインで字幕が映像から遅れて見える。動画後半ほどズレが目立つように体感される（実際は全区間で同じだが、後半の早口箇所で違和感が顕著化）。

**原因**: `estimate_offset_from_xml`（`whisper_to_srt.py:412-445`）が `start>0` の最初の audio clipitem を探す実装になっていた。本来「タイムライン頭に無音区間がある場合の補正」が目的だが、A1 トラックが 494 クリップに分割された動画（カット編集が細かい）では、`clip0.start=0`（先頭クリップ）が「>0」条件で除外され、`clip1.start=2.80`（隣接する 2 番目クリップ）を誤って拾ってしまう。

**前提の混同**: WAV ファイルが「タイムライン書き出し（カット済みレンダリング出力）」か「ソース録画」かでオフセット解釈が異なる。
- カット済み WAV → WAV time = timeline time → offset = 0
- ソース録画 WAV → タイムライン頭に無音があれば offset = clip0.start

**修正**（`whisper_to_srt.py:432-445`）:
- `if int(s) > 0` の条件を削除し、最初の有効 clipitem の `start` をそのまま採用
- カット済み WAV では clip0.start=0 → offset=0、ソース WAV では先頭の無音区間長 → offset>0、両方を正しく扱える

**判別の決め手（次回確認手順）**:
1. WAV の duration を `ffprobe` で取得
2. XML の audio track 0 最終 clip の `end` を取得（= timeline duration）
3. ほぼ等しければカット済み WAV、WAV>timeline ならソース WAV

**教訓**: オフセット計算は「複数クリップを舐めてフィルタする」より「先頭クリップの start を素直に使う」方が頑健。条件分岐を増やしてエッジケースを潰そうとすると、別のエッジケース（=細切れ編集）で誤検出する。

### v5 でのエージェント利用は避ける

**理由**: エージェント起動オーバーヘッドが 10〜20分単位で積み上がる。同じ作業をメインセッション内でやると数分で同等品質。

**例外**: 次回以降のセッションで、複数動画のバッチ処理や並列化が必要になった場合のみ検討。

## Why（視聴者体験の観点）

ユーザーは動画編集業界で「テロップの切り替えタイミング = 視聴体験の核」という認識を持っている。文字数ルールに従って機械的に切ると、単語途中や助詞直後で切れて「読めないテロップ」が生まれる。視聴者は "話の区切り" に合わせてテロップが切り替わることを期待しており、**意味境界優先は妥協不可の品質要件**。

## 関連ファイル

- `commands/srt.md` — v5 スキル定義（実行手順）
- `scripts/whisper_to_srt.py` — Whisper 転写 + `--from-text` SRT アセンブリ
- `memory/telop_channel_patterns.md` — チャンネル固有の固有名詞辞書

## 学習セッション: No.801 音声生成AI徹底比較（2026-04-12 / V4 メインテロップ）

ユーザーが完成版 XML を提供し、私の v2 出力 SRT と V4（発話連動メインテロップ）を比較学習した結果得られた**追加ルール**。

**スコープ**: V4 のみ。V5（強調/キーワード）、V1/V2/V3（タイトル・自己紹介・ラベル）は対象外。`/srt` が生成するのは V4 相当のテロップであり、学習対象はそこに限定する。

### 追加ルール 1: 「〜おり/ており」で積極的に切る

**例**（No.801 冒頭）:
- ✗ 私: `レベルになってきており人間が` + `話す必要は〜`
- ✓ 完成版 V4: `レベルになってきており` + `話す必要はなくなったんじゃないかというふうに`

**ルール**: 動詞連用形「〜おり」「〜ており」「〜まして」は**前の節の終止**として扱い、次テロップを新しい節で始める。「〜おり」の後ろに主語が続く場合、**主語は次テロップの頭に置く**。

### 追加ルール 2: 副詞句「徹底的に」「本当に」等は次テロップの先頭にできる

**例**（No.801）:
- ✗ 私: `人間と区別できなくなるのかというのを徹底的に` + `検証していきたいと思います`
- ✓ 完成版 V4: `人間と区別できなくなるのかというのを` + `徹底的に検証していきたいと思います`

**ルール**: 「徹底的に」「本当に」「しっかりと」「きちんと」等の程度副詞は、**後続の動詞に係る**ので、前テロップの末尾に置くより次テロップの先頭に置く方が自然。

### 追加ルール 3: 「ですけども」「なんですけど」で節を終えて切る

**例**（No.801）:
- ✗ 私: `今回なんですけどもより皆さんがAI音声だったりとか`（1テロップ）
- ✓ 完成版 V4: `今回なんですけども` + `より皆さんがAI音声だったりとか`

**ルール**: 「ですけども」「なんですけど」「ですが」で節を終えた後は、**フィラー・接続詞的トランジションであっても独立テロップ化**される。前後の内容を無理に繋げない。

### 追加ルール 4: 話題転換点（説明→CTA、概念→具体例）は必ず切る

**例**（No.801）:
- ✓ 完成版 V4: `今回の検証企画をより深く理解できるように` + `LINE登録者限定で`
  - 前後で「説明」→「CTA」の転換あり

**ルール**: 次のような転換点では前後を必ず独立テロップにする:
- 説明 → CTA（LINE登録、概要欄、QRコードへの誘導）
- 概念 → 具体例（「例えば」「こちら」「これは」等で始まる）
- 抽象 → 数値（「なんと○万文字」「○秒で」等）
- 肯定 → 疑問（「か」「ですか」で終わる問いかけ）

### 追加ルール 5: 半角スペース挿入は「話者ポーズ + 英語前後」の両方で実装

**完成版 V4 で観察された半角スペースの位置（8% = 55件）**:

1. **話者の息継ぎ**（word gap > 300ms 相当）:
   - `実は今 喋って`（「今」の後で一拍）
   - `ピッチ変えたり 音量ですね`（列挙の区切り）
2. **英語固有名詞の前後（境界マーカー）**:
   - `今回は本当に AI音声は`（日本語→英語）
   - `Sad 悲しいにしておきましょう`（英語→日本語の補足）
3. **英語内部の正規表記**:
   - `MiniMax Audio`、`Fish Audio`、`Sound Tag`、`Add Your Voice to the Mix`

**実装**: `whisper_to_srt.py` の半角スペース挿入条件を:
- 現在: `word gap > 0.3s` のみ
- 追加: **日本語→英数字の境界**、**英数字→日本語の境界**にも挿入（ただし既に英単語が半角スペースを含む場合はそのまま）

### 追加ルール 6: フィラー「こう」「ちょっと」は全削除禁止

**例**（No.801）:
- 完成版 V4 で「こう」が 5 回、「ちょっと」が 1 回残っている
- 私の SRT では両方 0 回 → 削りすぎ

**ルール**: `remove_fillers()` の対象から「こう」「ちょっと」を**除外**する。これらは文脈によって意味を持つ（副詞的用法、強調）ため一律削除は誤り。代わりに、**LLM の Step 3e で文脈判断で削除**する。

### 追加ルール 7: 英語プロダクト名は「正規表記 + 半角スペース」で統一

**CORRECTIONS 辞書に追加すべき No.801 由来のエントリ**（V4 で観測された正規表記）:

### 追加ルール 8: メタコメント・時間稼ぎフレーズは LLM が積極削除

**V4 で削除された典型パターン**:
- 「これを紹介したいだけがためにXXXの紹介を入れました」
- 「いいかなという感じはしますね」
- 「近づいてるなというのを感じました」
- 「じゃあこのまま生成していきます」（ナレーション埋め草）
- 「〜というふうに僕は思ってるんですけども」（主観表明の冗長形）

**ルール**: LLM の改行処理時に以下のパターンに該当するテロップは **削除候補** として扱う:
- 内容がない時間稼ぎ（「〜な感じがしますね」系）
- メタ言及（「〜を紹介したかっただけ」「〜を見せたかったから」）
- 主観表明の冗長形（「〜と思ってるんですけども」→「〜と思います」で十分）
- ナレーションの埋め草（処理中の合いの手）
